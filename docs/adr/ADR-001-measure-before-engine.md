# ADR-001: 계측기를 엔진보다 먼저 만든다 (역순 개발)

- 상태: Accepted
- 날짜: 2026-08-24
- 관련: P1, SC-1, SC-2, Round R1
- 개정: 2026-08-24 (codex 검토 [CRITICAL] "R1의 bench는 엔진 없이 엔진 통과를 수행할 수 없다" 반영)

## 맥락

돌파(fetch) 엔진은 "얼마나 잘 뚫는가"로만 평가된다. 그런데 프로젝트 착수 시점에
우리는 그 수치를 산출할 수단이 없다. 통상적 순서(엔진 먼저 → 나중에 벤치)로 가면
R2~R3의 모든 결정이 "이게 더 나을 것 같다"는 추측으로 정당화된다.
원본 insane-search가 MIT로 열려 있는 지금이 **대조군을 확보할 수 있는 유일한 창**이라는
사정도 있다. 대조 러너 없이 시간을 보내면 원본 유료화와 함께 기준점이 사라진다.

## 결정

**Round 1의 산출물은 "측정 가능한 최소 제품"이다.** 원칙은 "엔진을 늦춘다"가 아니라
**"측정 없는 개선을 금지한다"** 이다. 따라서 R1은 계측기와 **그 계측기가 통과시킬 최소 엔진**을
함께 담는다:

- 계측: 배터리 + 거버넌스(G-1~G-7), 러너, 결과 검증기(기대 정답 대조), 실패 사유 분류, 관측 로그 스키마
- 최소 엔진: **baseline transport**(표준 HTTP + 기본 임퍼소네이션 1종), 벤더 **라벨링** 최소 구현, 본문 추출
- 경계: 정책 가드(robots·rate limit·SSRF·인증정보 미취급) — 가장 위험한 route가 오기 전에 이미 있어야 한다
- 대조: 원본 대조 러너 (원본이 MIT인 창이 닫히기 전)

첫 결과물은 코드가 아니라 **수치 보고서 1장**이다:
"실제 리서치 실패율 Z%, Tier-1 돌파율 X%(3회 중앙값), 벤더별 분해, 원본 대비 Y%".

R2가 하는 일은 엔진을 만드는 것이 아니라 **이미 측정되고 있는 엔진을 최적화**하는 것이다
(격자 플래너, 벤더 프로파일 9종, Phase 0 인덱스, URL 변형).

### 초안에서 무엇이 틀렸나

초안은 R1에 계측기만 두고 curl_cffi를 R2에 두었다. 그러면 `bench`가 호출할 엔진이 없어
**아무 수치도 나오지 않고, A1(HTTP 계층만으로 얼마나 뚫리는가) 검증도 R2까지 미뤄진다.**
"엔진에 투자하기 전에 A1을 실측한다"는 취지가 스스로 무너진다. 그래서 개정했다.

## 결과

**좋아지는 것**
- R2 이후 모든 변경이 "돌파율 Δ"로 검증된다. 회귀가 즉시 보인다 (SC-2).
- 원본이 살아 있는 동안 대조 데이터를 확보해 SC-1의 동결 기준값을 얻는다.
- A1(HTTP 계층만으로 Tier-1의 40% 이상 통과)이 **격자 최적화에 투자하기 전에** 실측된다.
  40% 미만이면 R2 범위를 축소하고 R3(브라우저)를 앞당긴다 — 이 판정은 `by_route` 출력으로 자동화된다.
- 관측 로그 스키마가 R1에 고정되어, R1~R3 결과를 **동일 스키마로 비교**할 수 있다.
- 정책 가드가 R1에 있어, 브라우저 티어 도입 시점에 경계가 이미 코드로 존재한다.

**나빠지는 것 / 감수하는 것**
- 첫 1~2주 동안 "뚫는 기능"이 하나도 없다. 체감 진도가 느리다.
- 계측기가 엔진 인터페이스를 먼저 못박게 되어, R2에서 인터페이스 수정 비용이 발생할 수 있다.
  → 완화: R1의 엔진 접점은 `fetch(url) -> FetchResult` 단일 함수로 최소화한다.
- R1의 범위가 커져 "계측기 먼저"라는 표어보다 무겁다. 그래서 **종료 조건을 산출물이 아니라
  보고서 1장으로** 정의하고, Tier-1 규모 상한을 50 URL로 둔다 (G-6).

## 대안

- **엔진 먼저, 벤치 나중**: 통상적. 기각 — 개선을 검증할 수 없고, 원본 대조 창을 놓친다.
- **동시 진행**: 기각 — 계측 기준이 흔들리면 초기 수치가 서로 비교 불가능해진다.
- **계측기만 R1 (초안)**: 기각 — 측정할 대상이 없어 R1이 아무 수치도 산출하지 못한다 (위 "초안에서 무엇이 틀렸나").
