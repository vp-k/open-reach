# ADR-002: 사이트별 표 대신 WAF 벤더 타입으로 일반화

- 상태: Accepted
- 날짜: 2026-08-24
- 관련: P2, NG-8, NG-9, A2

## 맥락

"어떤 사이트를 뚫는가"를 사이트 목록으로 관리하는 방식은 두 가지로 실패한다.
(1) 목록에 없는 사이트를 만나면 아무 정보가 없다. (2) 사이트가 WAF 벤더나 설정을
바꾸면 항목이 조용히 썩는데, 썩었다는 사실이 드러나지 않는다.
반면 차단의 실체는 사이트가 아니라 **그 앞에 선 WAF 제품**이며, 제품은 소수다
(Cloudflare, Akamai, DataDome, PerimeterX/HUMAN, Imperva/Incapsula, AWS WAF,
Kasada, Queue-it + `unknown_challenge`). 각 제품은 응답에 공개적으로 문서화된
지문(쿠키명·헤더·상태코드·본문 마커)을 남긴다.

## 결정

**규칙의 단위는 사이트가 아니라 WAF 벤더다.** `profiles.yaml`에는 사이트 이름을 쓰지 않는다.
각 프로파일은 `detectors`(응답 신호) → `impersonate_candidates` / `avoid` /
`transform_order` / `fallback_order`를 담는다. 처음 보는 호스트도 응답 신호로
벤더가 판정되면 그 벤더의 전략이 즉시 적용된다.
벤더가 판정되지 않으면 `unknown_challenge` 프로파일의 보수적 격자를 쓴다.

## 결과

**좋아지는 것**
- 배터리에 없는 사이트에도 전략이 적용된다 (일반화).
- 유지보수 대상이 N개 사이트가 아니라 9개 프로파일로 고정된다.
- 사이트 이름이 코드/데이터에 없으므로 "특정 사이트를 겨냥한 도구"로 읽히지 않는다.

**나빠지는 것 / 감수하는 것**
- 같은 벤더를 쓰더라도 사이트별 설정 강도가 달라, 사이트 특화 대비 돌파율이 낮은 구간이 생긴다.
- 벤더 오분류 시 잘못된 전략을 전부 소진한 뒤 실패한다.
  → 완화: `WafVerdict.confidence`가 낮으면 `unknown_challenge` 격자로 폴백한다.

## 대안

- **사이트별 핸들러 테이블**: 기각 — NG-8/NG-9. 유지 불가능하고 신규 사이트에 무력하다.
- **무조건 브라우저 폴백**: 기각 — 느리고 무겁고, 왜 통과했는지 학습되지 않는다.
