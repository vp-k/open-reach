## 1. Problem Statement

- [MAJOR] “원본의 유료화 가능성”은 사용자 문제라기보다 구현·조달 리스크다. Problem Statement의 핵심 문제 1번은 제품이 해결할 사용자 고통이 아니라 “왜 지금 이 구현을 해야 하는가”에 가깝다.  
  고칠 것: 문제 정의에서는 “공개 근거에 접근 실패했을 때 리서치 품질·완결성·재현성이 어떻게 손상되는가”만 다루고, 원본 유료화는 별도 `Build vs. dependency ADR`로 분리하라.

- [MAJOR] To-Be가 “자체 엔진”, “돌파율”이라는 해법을 미리 확정한다. 사용자가 원하는 것은 접근 가능한 공개 근거와 실패의 설명이지 curl/TLS/브라우저 폴백이 아니다.  
  고칠 것: To-Be를 “정책상 허용되는 공개 접근 경로를 시도하고, 결과·한계·근거를 재현 가능하게 남긴다”로 바꾸고, 자체 엔진은 가설적 수단으로 낮춰라.

- [MAJOR] “중요한 소스가 막혀 리서치가 편향된다”는 핵심 주장에 현재 규모·빈도·영향 데이터가 없다. P1 한 명의 경험을 일반 문제로 확장하고 있다.  
  고칠 것: 최근 실제 리서치 표본에서 URL 수, 표준 fetch 실패율, 실패가 결론/작업시간에 미친 영향, 대체 소스 유무를 수집해 기준선으로 넣어라.

## 2. Success Criteria와 배터리 조작 가능성

- [CRITICAL] SC-1은 원본이 사라지면 의미 있는 경쟁 기준이 아니라 과거의 스냅샷이 된다. “마지막 원본 수치”는 당시 네트워크, IP 평판, 원본 버전, 대상 사이트 상태를 함께 보존하지 않으면 재현도 비교도 불가능하다.  
  고칠 것: SC-1을 출시 게이트가 아닌 초기 역량 검증으로 한정하라. 원본 실행 가능한 컨테이너/커밋 SHA, 실행 일시, OS·네트워크 조건, 원본별 결과 원문을 증적물로 동결하고, 이후에는 독립적인 고정 검증 스위트를 기준으로 삼아라.

- [CRITICAL] SC-2의 Tier-1 `≥80%`는 배터리 설계자가 쉬운 URL을 넣거나 어려운 URL을 Tier-2로 내리면 조작된다. 현재 배터리 선정권, 티어 기준, 변경 승인, URL 교체 규칙이 없다.  
  고칠 것: 벤치마크 거버넌스를 명문화하라. 벤더·난이도·콘텐츠 유형별 최소 할당, 사전 정의된 포함/제외 기준, URL 교체 시 이전 항목과 사유 보존, 배터리 변경 PR 분리, 결과 공개, 릴리즈 시 고정된 holdout 배터리를 의무화해야 한다.

- [CRITICAL] “본문 추출 성공”은 진짜 공개 본문을 얻었다는 뜻이 아니다. 오류 페이지, 짧은 미리보기, 검색 결과, 동의 배너, 기사 첫 문단, soft paywall을 성공으로 세면 수치가 부풀려진다.  
  고칠 것: 각 배터리 항목에 기대 본문 식별 기준(최소 본문 길이만이 아닌 제목·핵심 문자열·정규화 해시 또는 사람 검수된 정답 판정)을 두고, 성공 검증을 URL별 기대값과 대조하라.

- [MAJOR] SC-3 “오탐 0”은 측정 방법과 모수가 없다. 모든 로그인월·페이월·챌린지 변형을 알 수 없으므로 “0건”은 실제 무오탐이 아니라 미발견일 수 있다.  
  고칠 것: 라벨링된 wall/challenge 음성 테스트셋과 공개 본문 양성 테스트셋을 만들고, 정확도·재현율·미분류율을 각각 측정하라. 특히 `success` 판정은 고신뢰 기준을 만족하지 않으면 실패/미분류로 보수적으로 처리하라.

- [MAJOR] SC-4의 100% 분류는 실패 원인을 안다는 뜻이 아니다. `unsupported`에 모든 모르는 실패를 넣으면 100%가 된다. 현재 분류 체계에는 `unknown`, `policy_blocked`, `validation_failed`, `rate_limited`, `server_error`도 없다.  
  고칠 것: 관측된 신호와 추론된 원인을 분리하라. 예: HTTP 상태·리디렉션·본문 시그널은 사실로 기록하고, 사유는 신뢰도와 함께 반환하라. `unknown`을 허용하되 원인 없는 성공/침묵만 금지해야 한다.

- [MAJOR] 단일 `bench` 실행 수치는 WAF의 시간대, IP 평판, 지역, 일시 장애에 매우 민감하다. 한 번의 실행으로 회귀나 개선을 판정하면 우연을 제품 성과로 오인한다.  
  고칠 것: 고정 실행 환경에서 반복 실행, 중앙값/신뢰구간, 벤더별 하한, 연속 N회 회귀 조건을 정의하라. 전체 비율만으로 릴리즈를 통과시키지 말고 Tier-1 및 각 핵심 벤더 하한을 별도 게이트로 둬라.

- [CRITICAL] SC-5의 자동 갱신은 성능 피드백 루프가 정책 위반 또는 오탐을 “학습”하는 통로가 될 수 있다. 수치가 높아지는 후보만 남기는 자동 갱신은 차단 회피 강도를 자동 증폭시킨다.  
  고칠 것: `refresh`를 자동 적용이 아닌 후보 생성으로 제한하고, 정책 검사·holdout 재검증·변경 diff 검토·롤백·만료일을 통과해야 반영되게 하라. 프로파일별 허용 행동을 코드상 allowlist로 고정하라.

## 3. 핵심 가정 검증의 결함

- [CRITICAL] A1 검증이 “Phase A 배터리 1회 실행”뿐이다. “상당수”의 정의도 없고, curl_cffi를 아직 R2에 두어 R1만으로 검증할 수도 없다.  
  고칠 것: R1 말미에 최소 TLS 프로토타입을 포함하고, 사전 등록한 표본·holdout·반복 실행으로 “허용 범위 내 공개 URL 중 무엇을 얼마나 개선하는가”를 검증하라. 기준 미달 시 R2 투자 중단 또는 방향 전환이라는 go/no-go 조건도 적어라.

- [CRITICAL] A2는 10종 내외라는 벤더 수 가정과 “벤더 단위 일반화”를 동시에 검증하지 않는다. 미등록 사이트를 넣는다고 정답 벤더와 일반화 성능이 자동으로 검증되지 않는다.  
  고칠 것: 학습용 도메인과 완전히 분리된 도메인 holdout을 벤더별로 구성하고, WAF 판별 정확도·미확인 벤더 처리율·각 벤더 프로파일의 성공률을 분리 측정하라. `unknown vendor`가 안전하게 멈추는 정책도 가정에 추가하라.

- [MAJOR] A3는 동일 URL 2회차 시간 비교만으로 가치가 증명되지 않는다. 서버 캐시, 네트워크 변동, 콘텐츠 변경 때문에 경로 재사용 효과와 구분되지 않는다.  
  고칠 것: 동일 조건의 대조 실험에서 평균 시도 횟수, p95 지연, 성공률, 잘못 재사용해 악화된 비율을 측정하고, 재사용 TTL·무효화 규칙을 명시하라.

- [MAJOR] A4는 “시드가 유효한가”만 보며, 시드의 출처·라이선스·유지 책임·안전성을 검증하지 않는다. 원본의 데이터가 코드와 분리 가능한지도 불명확하다.  
  고칠 것: 시드별 출처 URL, 취득 일시, 라이선스 근거, 원본 변경분과의 관계, 제거 절차를 포함한 provenance manifest를 만들고 clean-room 규칙을 정하라.

- [MAJOR] A5를 “릴리즈 후 P2 피드백”으로 검증하면 이미 설치·배포 구조를 확정한 뒤다. 150~400MB 다운로드와 브라우저 실행은 기업 장비, 오프라인 환경, 보안 정책에서 즉시 실패할 수 있다.  
  고칠 것: R3 이전에 신규 사용자 설치 테스트를 하고, 다운로드 실패율·설치 시간·디스크 요구량·브라우저 실행 허용률을 출시 게이트로 둬라.

- [MAJOR] A6의 실패 사유 분포는 사용자 요구의 대부분이 공개 콘텐츠로 충족된다는 증거가 아니다. 배터리와 사용자 행동이 이미 공개 URL에 편향돼 있기 때문이다.  
  고칠 것: 실제 리서치 과업 단위로 필요한 출처, 접근 불가 사유, 대체 소스 가능 여부, 최종 과업 완료 여부를 기록해 검증하라.

- [CRITICAL] A7은 “정책 문서화”로 검증될 수 없다. robots/ToS가 도구 목적과 충돌하지 않는다는 가정은 사이트·관할·사용 맥락별로 달라지고, WAF 우회 자체가 명시적 제한의 회피로 해석될 위험이 있다.  
  고칠 것: Phase 1 이후가 아니라 R1 이전에 적용 관할, 허용 대상, robots/ToS 처리 원칙, 금지 신호, 중단 기준, 사용자 고지와 책임 분담을 정책으로 확정하고 실행 코드의 테스트 게이트로 만들어라.

- [MAJOR] 브라우저 폴백이 사용자 인증정보 없이도 안정적으로 작동하고, patchright의 stealth 성격이 경계 정책과 양립한다는 가정이 빠져 있다.  
  고칠 것: 별도 고위험 가정으로 등록하고, 브라우저 단계에서 허용되는 자동화 행동·프로필 격리·챌린지 감지 후 즉시 중단을 검증 대상으로 삼아라.

## 4. Non-Goals의 강제 가능성

- [CRITICAL] NG-1~NG-3은 선언일 뿐 감지 실패 시 우회가 계속될 수 있다. 특히 Phase 1→2→3 폴백은 로그인월·soft paywall·JS 챌린지를 정확히 구분하지 못하면 금지된 대상으로 더 강한 경로를 시도한다.  
  고칠 것: 모든 route 앞에 정책 판정 게이트를 넣고, 벽 신호가 하나라도 있으면 후속 route를 차단하는 불변 테스트를 작성하라. 챌린지는 “해결 시도 금지 및 중단”인지, 단순 공개 JS 렌더링은 허용인지도 명시적으로 구분하라.

- [CRITICAL] NG-4는 관측 로그와 브라우저가 정면으로 충돌한다. URL query, 리디렉션 URL, 응답 헤더, Chromium 프로필·캐시에는 토큰·식별자·쿠키가 남을 수 있다.  
  고칠 것: 영속 브라우저 프로필을 금지하고 매 실행 임시·격리 컨텍스트를 사용하라. 로그는 query/헤더/본문을 기본 비저장 또는 redaction하고, 보존 기간·삭제 명령·비밀 스캔 테스트를 계약에 넣어라.

- [MAJOR] NG-5와 NG-6은 CLI 반복 호출과 `bench`에 의해 쉽게 무력화된다. 단건 API라도 루프 호출하면 크롤러이고, 프록시를 사용하지 않는다고 해도 호스트별 과도한 요청은 발생한다.  
  고칠 것: 호스트별 동시성 1, 요청 예산, 최소 간격, 백오프, 실행당 최대 시도 수, 전역 차단 목록을 강제하라. `bench`에는 운영 사이트에 대한 별도 낮은 속도와 재개 규칙을 둬라.

- [MAJOR] NG-7은 코드 벤더링만 금지한다. 원본의 프로파일·후보 순서·주석·측정 데이터가 실질적 복제인지 판단할 절차가 없다.  
  고칠 것: 외부 자료 반입 심사, 출처 manifest, 라이선스 고지, 원본과의 텍스트/구조 유사성 리뷰, 독자 생성 데이터로의 교체 계획을 강제하라.

- [MAJOR] NG-8은 마케팅·문서 통제 없이는 강제되지 않는다. 코드에 있는 벤더 프로파일, README, 릴리즈 노트가 “지원” 주장으로 읽힐 수 있다.  
  고칠 것: 공개 문서와 CLI 도움말에서 지원 주장 문구를 CI로 검사하고, “배터리에서 검증된 URL/조건”만 자동 생성해 표시하라.

- [MAJOR] NG-9의 “벤더 9종 제한”은 `profiles.yaml`에 사이트 예외와 후보가 계속 쌓이면 쉽게 무너진다. Phase 0 공개 API 인덱스와 yt-dlp 라우팅도 사실상 플랫폼별 특별 취급이다.  
  고칠 것: 허용된 플랫폼 어댑터의 근거와 상한을 별도 정책으로 정의하고, 호스트명 기반 분기·예외 규칙을 CI에서 차단하라. 프로파일 추가는 벤더 증거와 holdout 성능 증명을 요구하라.

- [MAJOR] NG-10은 SC-4의 닫힌 분류 체계와 충돌한다. 알 수 없는 실패를 억지로 분류하면 fail-loud가 아니라 잘못된 확신을 준다.  
  고칠 것: `unknown`과 신호 원문을 허용하고, 사용자 출력에는 “알 수 없음”을 분명히 표시하며 후속 시도 중단 여부를 함께 반환하라.

## 5. Round 배치의 의존성 오류

- [CRITICAL] R1의 `bench`는 엔진 없이 “엔진 통과”를 수행할 수 없고, A1 검증도 curl_cffi가 R2라면 할 수 없다. 역순 개발 논리와 실제 배치가 충돌한다.  
  고칠 것: R1에 최소 실행 경로(표준 fetch + curl_cffi 실험 어댑터), 배터리, 기대값 검증기, 로그 스키마를 포함하라. 완성 엔진이 아니라 측정을 위한 최소 프로토타입이어야 한다.

- [CRITICAL] WAF 타입 감지기가 R2인데 R1은 벤더별 배터리와 실패 사유를 측정하려 한다. 벤더 판별 정의·정답 라벨·신뢰도 모델 없이 벤더별 수치는 성립하지 않는다.  
  고칠 것: R1에서 판별 신호 수집과 `unknown_vendor`를 먼저 구현하고, R2에서 프로파일 기반 플래너를 추가하라.

- [CRITICAL] SC-1 대조 러너를 R3에 두면 “원본이 아직 비교 가능한 창”이라는 착수 근거를 스스로 놓친다. R3 도달 전에 원본 또는 실행 환경이 사라질 수 있다.  
  고칠 것: R1에서 원본 대조를 재현 가능한 증적 수집 작업으로 실행해 결과를 동결하라. R3에는 대조 러너 개선만 남겨라.

- [MAJOR] 관측 로그는 R3이 아니라 R1부터 필요하다. 그렇지 않으면 R1/R2 결과를 동일한 관측 스키마로 비교할 수 없고, 이후 학습 데이터도 결측된다.  
  고칠 것: R1에서 append-only 이벤트 스키마·redaction·실행 환경 메타데이터를 고정하고 모든 route가 이를 기록하게 하라.

- [MAJOR] `refresh`가 R4인 것은 R2의 `profiles.yaml`을 수동으로 유지하겠다는 뜻이 된다. P5 및 SC-5와 충돌한다.  
  고칠 것: R2에는 최소한 후보 생성과 만료 경고를 넣고, R3에서 안전한 검증·승격 절차를 넣어라. R4에는 패키징 자동화만 남겨라.

- [MAJOR] 정책·법적 경계가 브라우저 폴백 이후에만 실질화될 위험이 있다. 브라우저는 가장 높은 위험의 route인데 R3 진입 게이트가 없다.  
  고칠 것: R3 시작 전 정책 테스트, 도메인/네트워크 차단, rate-limit, 챌린지 중단이 모두 통과해야 브라우저 route를 활성화하게 하라.

- [MINOR] SKILL.md와 패키징을 R4에 미루면 P2 설치성 검증도 R4까지 미뤄진다. A5의 조기 검증과 맞지 않는다.  
  고칠 것: R2 또는 R3에 최소 패키지 설치 경로를 만들고, 실제 깨끗한 환경에서 설치 테스트를 실행하라.

## 6. 문서가 놓친 법적·윤리적 리스크

- [CRITICAL] “공개 콘텐츠”는 자동 접근·보안 조치 우회 허가를 뜻하지 않는다. robots.txt, 사이트 ToS, WAF의 접근 제한, 관할별 컴퓨터 접근·기술적 보호조치 규정은 서로 별개다.  
  고칠 것: 서비스 대상 관할과 허용 사용 정책을 정하고, robots/ToS/명시적 자동화 금지 신호에 대한 기본 거부 원칙, 예외 승인 주체, 사용자 고지를 문서와 코드로 정하라.

- [CRITICAL] patchright 및 실브라우저 기반의 anti-bot 대응은 “공개 정보 접근”보다 보안·봇 탐지 회피로 보일 수 있다. CAPTCHA를 풀지 않더라도 탐지 회피 자체의 위험은 남는다.  
  고칠 것: stealth/anti-detection 기능을 허용 범위에서 제외하거나, 어떤 경우에 브라우저 렌더링만 허용되는지 엄격하게 정의하라. 탐지·챌린지 신호가 있으면 자동 중단하고 사용자가 직접 재시도해도 자동화 경로가 강화되지 않게 하라.

- [MAJOR] 임의 URL fetch는 내부 IP, localhost, 클라우드 메타데이터 주소, 리디렉션을 통한 SSRF성 접근에 악용될 수 있다. Claude Code 플러그인이라면 특히 사용자 로컬 네트워크에서 실행된다.  
  고칠 것: HTTP(S)만 허용하고, 사설·루프백·링크로컬·메타데이터 IP 및 DNS 재해석을 차단하며, 리디렉션마다 재검증하라.

- [MAJOR] JSONL 관측 데이터는 URL의 개인식별 query, 사용자가 조사한 주제, 응답 메타데이터를 장기 보관할 수 있다. 이는 개인정보·민감 관심사·업무 기밀 문제로 이어진다.  
  고칠 것: 데이터 최소화, 기본 로컬 저장 여부, 암호화/권한, 보존 기간, 삭제, 익명화, 원격 전송 금지를 명시하라.

- [MAJOR] Markdown 추출 결과의 보관·재배포·후속 LLM 입력은 저작권, 데이터베이스 권리, 사이트별 이용 범위를 침해할 수 있다. 페이월이 아니어도 재이용 허가가 자동으로 생기지 않는다.  
  고칠 것: 결과를 원문 대체물로 장기 저장·배포하지 않는 기본 정책, 출처·취득 시각·라이선스 불명 표시, 사용자 책임 고지를 추가하라.

- [MINOR] yt-dlp와 플랫폼 공개 API의 이용약관·지역 제한·미디어 저작권 리스크가 별도 검토되지 않았다.  
  고칠 것: 플랫폼별 어댑터 허용 목록과 금지 대상, 자막·미디어의 저장 금지 또는 명시적 사용자 확인 규칙을 정책에 넣어라.

## 7. 6개월 뒤 실패 pre-mortem

1. [CRITICAL] WAF와 브라우저 탐지가 더 빨리 변해 벤더 공통 규칙이 실제로 일반화되지 않는다. 성공률은 일부 익숙한 도메인에서만 유지되고, 신규 도메인은 `unknown` 또는 반복 차단된다.  
   고칠 것: 신규 도메인 holdout 성능과 벤더별 하한을 월별로 공개하고, A1/A2 실패 시 브라우저 강화가 아니라 “지원 범위 축소 또는 제품 재정의”로 전환하는 기준을 지금 정하라.

2. [CRITICAL] 배터리가 쉬운 정적 URL과 이미 성공한 경로 중심으로 진화해 전체 돌파율은 높지만 실제 리서치 실패는 줄지 않는다.  
   고칠 것: 독립 holdout, URL 교체 감사 이력, 벤더·난이도별 최소 쿼터, 실제 리서치 과업 완료율을 릴리즈 게이트에 추가하라.

3. [CRITICAL] 정책·ToS·네트워크 평판·브라우저 설치 문제 때문에 실제 사용 환경에서 비활성화되거나 사용이 중단된다. 기능이 있어도 기업 장비에서 Chromium을 설치하지 못하고, 사이트는 반복 접근을 차단하며, 배포자는 책임을 감당하지 못한다.  
   고칠 것: R1부터 정책 차단·속도 제한·SSRF 방어를 구현하고, R3 전에 깨끗한 환경 설치 시험과 실제 사용자 리서치 파일럿을 통과해야 공개 배포하게 하라.
